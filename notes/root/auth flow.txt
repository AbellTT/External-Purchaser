1. User registers
The user goes to:
/signup
They fill in the registration information and submit.
Frontend
The signup page dispatches:
dispatch(register(formData))
The register thunk calls:
POST /api/auth/register
with the registration information.
For example:
{
  "email": "...",
  "password": "...",
  "organizationName": "...",
  "organizationType": "...",
  "phoneNumber": "...",
  "tinNumber": "...",
  "address": {
    ...
  }
}
2. Django processes registration
The backend:
POST /auth/register
        │
        ▼
Validate registration data
        │
        ├── invalid → 400
        │
        ▼
Create User
        │
        ▼
Create organization/profile data
        │
        ▼
Create UserSession
        │
        ▼
Generate access token
        │
        ▼
Generate refresh token
The refresh token contains your session_id.
Your session has things such as:
UserSession
├── user
├── is_active = True
├── session_expires_at
├── remember_me
└── ...
The backend then returns the access token and refresh token.
The refresh token is placed into the:
HttpOnly refreshToken cookie
The browser stores that cookie.
JavaScript cannot read it.
3. Redux receives the registration result
Your register.fulfilled reducer does:
state.user = action.payload.user
state.accessToken = action.payload.accessToken
state.isAuthenticated = true
and stores the user information locally:
localStorage.setItem('user', ...)
So immediately after registration:
Redux
├── user           = registered user
├── accessToken    = short-lived JWT
├── isAuthenticated = true
└── loading        = false
Browser cookie:
refreshToken = HttpOnly refresh JWT
4. User is now inside the dashboard
The user navigates to:
/dashboard
The ProtectedRoute checks Redux:
selectIsAuthenticated
and sees:
true
So the dashboard renders.
Every API request made through your api Axios instance goes through the request interceptor.
The interceptor takes:
state.auth.accessToken
and adds:
Authorization: Bearer <access-token>
The browser also automatically sends the HttpOnly refresh cookie because:
withCredentials: true
5. User continues using the dashboard
Normal request:
React
  │
  ▼
api.get('/something')
  │
  ▼
Axios request interceptor
  │
  ▼
Authorization: Bearer <accessToken>
  │
  ▼
Django
If the access token is still valid:
200 OK
Nothing special happens.
6. Access token expires
Eventually the access token expires.
The important thing is:
The refresh token does not necessarily expire at the same time.
Suppose the browser makes:
GET /api/user/profile
The access token is expired.
Django/SimpleJWT responds:
401 Unauthorized
Then Axios catches the 401.
7. Axios automatically refreshes
Your response interceptor sees:
401
It checks that this isn't:
/auth/refresh
and that the request hasn't already been retried.
Then it calls:
POST /api/auth/refresh
The browser automatically attaches:
Cookie: refreshToken=...
because:
withCredentials: true
There is no need for localStorage to contain the refresh token.
8. Django validates the refresh session
Your RefreshView does something important.
It first reads the token without enforcing JWT exp:
decode(refresh_token, verify=False)
Then it checks:
token_type == refresh
Then:
session_id
Then it retrieves:
UserSession
Then:
session.is_active
Then:
session.session_expires_at
So there are effectively two levels of expiration:
Access JWT expiration
        ↓
Short-lived
        ↓
Can be refreshed

UserSession expiration
        ↓
Long-lived/fixed session lifetime
        ↓
When this expires, the session is dead
9. If the session is still valid
Django generates:
new access token
new refresh token
The refresh token is returned and the cookie is replaced.
The response is:
{
  "success": true,
  "data": {
    "accessToken": "...",
    "refreshToken": "..."
  }
}
Your Axios interceptor takes the new access token:
storeReference.dispatch(
  setAccessToken(accessToken)
)
Then it puts the new token onto the original request:
Authorization: Bearer <new-access-token>
and retries the original request.
So from the user's perspective:
GET /profile
   ↓
401
   ↓
refresh
   ↓
new access token
   ↓
retry /profile
   ↓
200
The user doesn't see any of this.
10. User refreshes the browser while on the dashboard
This is an important distinction.
When the browser performs:
F5
Redux memory disappears.
Therefore:
accessToken = null
because we deliberately do not persist the access token.
But the browser still has:
HttpOnly refreshToken cookie
and we have the user information in localStorage.
The application starts.
Your current architecture should therefore do authentication initialization for protected/dashboard areas, rather than treating the login page as something that needs to refresh the session.
The desired sequence is:
Dashboard loads
      ↓
No access token in Redux
      ↓
Initialize/restore authentication
      ↓
POST /auth/refresh
      ↓
Browser automatically sends refresh cookie
      ↓
Django validates UserSession
      ↓
new access token
      ↓
Redux.accessToken = new token
      ↓
isAuthenticated = true
      ↓
Dashboard renders
That's why the dashboard can survive a hard refresh.
11. What happens if the refresh token/session is expired?
Suppose:
UserSession.session_expires_at
has passed.
The browser sends:
POST /auth/refresh
Django finds the session and does:
if timezone.now() >= session.session_expires_at:
    session.is_active = False
and returns:
401 Unauthorized
The important part is:
session.is_active → False
So the backend has now permanently invalidated that session.
The frontend then:
clearAuth()
which results in:
user = null
accessToken = null
isAuthenticated = false
Then the protected route redirects the user to:
/login
12. What happens on the login page?
This is where we fixed the problem you had earlier.
The login page should not attempt to initialize authentication.
It should simply be:
/login
The user enters credentials.
Then:
POST /auth/login
If successful:
access token
+
refresh cookie
are established.
Redux becomes:
isAuthenticated = true
accessToken = ...
user = ...
Then the user goes to:
/dashboard
So we don't want:
/login
   ↓
initializeAuth
   ↓
/auth/refresh
   ↓
401
   ↓
/login
   ↓
initializeAuth
   ↓
...
That was the infinite loop you encountered.
13. User logs out normally
The user clicks:
Logout
Frontend:
dispatch(logout())
which calls:
POST /api/auth/logout
The browser automatically sends:
refreshToken cookie
Django:
decode refresh token
        ↓
get session_id
        ↓
blacklist refresh token
        ↓
UserSession.is_active = False
        ↓
delete refreshToken cookie
        ↓
200 OK
You already tested this successfully.
You got:
200 OK
and:
Set-Cookie:
refreshToken="";
expires=Thu, 01 Jan 1970 00:00:00 GMT;
Max-Age=0;
and your database showed:
is_active = false
That's exactly what we want.
14. Redux then logs the user out
The logout.fulfilled reducer does:
state.user = null
state.accessToken = null
state.isAuthenticated = false
and removes the stored user:
localStorage.removeItem('user')
So now the browser has:
Redux:
accessToken = null
user = null
isAuthenticated = false

Cookie:
refreshToken = deleted
The protected route sends the user to:
/login
15. What happens if logout fails?
You deliberately designed logout to be resilient:
try {
    await api.post('/auth/logout')
} catch {
    console.error(...)
}
Then Redux still clears the local authentication state.
That's generally useful because the user clicked Logout, so the UI should log them out even if the network is unavailable.
However, there is one subtle backend concern we'll want to revisit later:
If the logout request never reaches Django, the server-side session may remain active.
The browser still loses its cookie only if the server response deletes it, so in a network failure the cookie may remain.
But the frontend is still logged out.
16. User logs in again after logging out
This creates a new session.
That's important.
Suppose:
Session A
is_active = false
User logs in again.
Django creates:
Session B
is_active = true
So we don't resurrect Session A.
Instead:
old session
    ↓
inactive

new login
    ↓
new session
    ↓
active
That's exactly what you meant earlier by:
even if they login they will have just another session
Yes.

19. The three things that represent authentication
This is probably the most useful mental model for the whole system.
Access token
Where: Redux memory
Lifetime: short
Purpose: authorize API requests
Persisted: NO
If the browser refreshes:
gone
That's intentional.
Refresh token
Where: HttpOnly cookie
Lifetime: tied to session/refresh policy
Purpose: obtain new access tokens
Persisted: browser cookie
JavaScript can read it: NO
If the browser refreshes:
still there
assuming it hasn't expired/deleted.
UserSession
Where: Django database
Purpose: server-side control over the login session
It gives you the ability to say:
is_active = false
and kill the session server-side.
That's what makes your system more controllable than simply relying on JWT expiration.
